## 1. เจตนา — ทำไม / ทำไมตอนนี้

ทุกงานของโรงพิมพ์มี **ใบเสนอราคาใน Peak ก่อนเปิดใบสั่งงานเสมอ** (คุณนุ๊กยืนยัน) แต่วันนี้การเปิดใบสั่งงานต้องเปิดแดชบอร์ดแล้วพิมพ์ชื่อลูกค้า ชื่องาน จำนวน รายละเอียด ซ้ำกับที่อยู่ใน Peak แล้วทั้งหมด

Peak เปิด MCP (ส.ค. 2026) และเราพิสูจน์แล้ว (2026-11-14) ว่าเซิร์ฟเวอร์เรียกได้เองโดยไม่ต้องเปิดคอม งานอ่านไม่กินเครดิต คุณนุ๊กเป็น PRO Plus อยู่แล้ว

ต้องการให้ **ทีมรับออเดอร์ (นุ๊ก กิ๊ฟ เจี๊ยบ) พิมพ์คำสั่งในกลุ่ม LINE ทีม แล้วน้อง PP ดึงใบเสนอราคา + ลูกค้าจาก Peak มาเปิดใบสั่งงานให้** — จากมือถือ ไม่ต้องเปิดอะไรเพิ่ม ไม่ต้องพิมพ์ซ้ำ และทุกคนในกลุ่มเห็นว่าใครเปิดงานอะไร

## 2. Goals / Non-goals / Anti-goals

**Goals**
- `/order …` ในกลุ่ม LINE ที่อนุญาต → ร่างใบสั่งงานจากใบเสนอราคา Peak → เลือกหน่วย → เลือกกราฟฟิก → เลือกส่งต่อพิมพ์ → เลือกวันส่ง → ยืนยัน → **order + job ขึ้น /board รูปทรงเดียวกับที่สร้างจากฟอร์ม** (หน้าแก้ไข + หน้าพิมพ์ใบสั่งงานใช้ได้ตามปกติ)
- ที่การ์ดสรุป เลือกได้ว่าจะ **สร้างงานเลย** หรือ **บันทึกเป็นใบร่างในแดชบอร์ด** (ใบร่างที่มีข้อมูลจาก Peak + ทุกอย่างที่เลือกใน LINE ไว้เติมสเปกในคอมก่อนปล่อยเข้าผลิต)
- จำเลขใบไม่ได้ก็หาได้: ค้นด้วยชื่อลูกค้า เลขบางส่วน หรือชื่อลูกค้า + คำในชื่องาน
- **ไม่มี AI ในเส้นทางนี้เลย** (บอทคำสั่งล้วน — เร็ว ผลแน่นอน ไม่มีค่าใช้จ่ายต่อครั้ง) และ **ไม่กินเครดิต Peak** (ใช้ทูลอ่านอย่างเดียว)
- เชื่อมต่อ Peak ครั้งเดียวจากหน้าแอดมิน แล้วระบบต่ออายุ token เองตลอด · ถ้าการเชื่อมต่อพัง ต้อง **มีคนรู้**
- ชิ้นส่วนพื้นฐาน (ที่เก็บ token, Peak client, การรับปุ่มกดจากกลุ่ม) ใช้ต่อในเฟส 2 ได้

**Non-goals (เฟส 1 ไม่ทำ)**
- ไม่เขียนอะไรลง Peak (สร้าง/อนุมัติ/ยกเลิกเอกสาร) — เฟส 2
- ไม่ให้ AI อ่านข้อความรายการแล้วติ๊กช่องสเปก (ขนาด กระดาษ สี เคลือบ ฯลฯ) — คุณนุ๊กเลือก "ลอกข้อความลงหมายเหตุก่อน แล้วค่อยเพิ่มทีหลัง"
- ไม่รับคำสั่งแบบประโยคยาว ("น้อง PP เปิดงานไวนิลของ…ให้หน่อย") — คุณนุ๊กเลือกแบบคำสั่งก่อน
- ไม่แก้สเปกใน LINE — แก้ในแดชบอร์ดหลังสร้าง
- ไม่รองรับ photobook order type
- ไม่เปิดให้แชต 1-1 หรือกลุ่มลูกค้าใช้

**Anti-goals (ถ้าเกิดถือว่าพัง)**
- ใบสั่งงานซ้ำจากการกดซ้ำ / LINE ส่ง webhook ซ้ำ / สองคนเปิดใบเดียวกัน
- มอบหมายงานผิดกฎของฟอร์ม (เช่น ไม่มีทั้งกราฟฟิกและเครื่องพิมพ์) แล้วงานหลุดขึ้นบอร์ด
- บอทตอบโต้ข้อความคุยทั่วไปในกลุ่ม
- กลุ่มลูกค้า (ที่ลงทะเบียนไว้ใช้ `/track`) ใช้ `/order` ได้ หรือรู้ว่ามีคำสั่งนี้ หรือเห็นข้อมูล Peak
- token Peak รั่ว (ใน log, ใน DB แบบ plain text, ใน response)
- การเชื่อมต่อ Peak ตายเงียบ ๆ
- พฤติกรรมของฟอร์มเปิดใบสั่งงานเดิม (`POST /api/orders/add`) เปลี่ยน

## 3. ข้อจำกัด / ของเดิมที่ต้องเคารพ

**ฝั่ง LINE / dashboard (อ่านจากโค้ด 2026-11-14)**
- `app/api/ai-quote/line/route.ts` ตอบ 200 ทันทีแล้วทำงานใน `after()` · `maxDuration = 60`
- **ไม่มี dedupe ของ webhook event** — LINE redelivery จะถูกประมวลผลซ้ำ
- `parseLineEvents` (`lib/ai-quote/channels/line.ts`) ทิ้ง postback และรูปจากกลุ่ม/ห้อง รับเฉพาะข้อความ · `routeInbound` (`lib/ai-quote/webhook-router.ts`) ให้ข้อความกลุ่มที่ไม่ใช่ `/groupid` `/track` เป็น `ignore`
- ตอบด้วย reply token ก่อน (ฟรี) แล้ว fallback เป็น push (กินโควตา) · reply ละไม่เกิน 5 messages · ยังไม่มี Flex ที่ใช้ action แบบ `postback` ที่ไหนเลย และไม่มี helper กลางสำหรับสร้าง bubble
- ตรรกะสร้างออเดอร์อยู่ใน route เท่านั้น (`createOrder()` เป็น private, คืน `NextResponse`) — ไม่มีฟังก์ชันฝั่ง server ให้ webhook เรียก
- กฎของฟอร์ม: ต้องมี `name` `customer` `dateDue` `orderer` และ `assignStaff` (กราฟฟิก) **หรือ** `forwardPrint` (เครื่องพิมพ์) อย่างน้อยหนึ่ง · มีกราฟฟิก → `assignDept='graphic'` งานเริ่มที่กราฟฟิก และ `forwardPrint` ถูกเก็บไว้ในใบ · ไม่มีกราฟฟิก → `assignDept='print'` งานเข้าคิวเครื่องนั้น
- `orderer` เป็นรายชื่อตายตัว `ORDERERS = ['นุ๊ก','กิ๊ฟ','เจี๊ยบ']` (อยู่ใน `app/board/order-form.tsx`) · พนักงานอยู่ใน `STAFF` (`lib/board.ts`) · **ไม่มีตาราง users และไม่มี mapping LINE userId → คน**
- `details` / `rawData` ของ order = snapshot ของฟอร์มทั้งก้อน (`OrderFormData`, `emptyOrderForm()` ใน `lib/photobook.ts`) · route แก้ไขสร้าง snapshot ใหม่จาก body ของฟอร์ม → **key นอกฟอร์มใน snapshot หายเมื่อมีคนกดแก้ไข**
- ฟอร์มปัจจุบันไม่กรอก `price` (ส่ง `''`)
- DDL ทั้งหมดอยู่ใน `app/api/admin/db-migrate/route.ts` (admin กด GET) — ไม่มี migrations folder · ไม่มีตารางเก็บ secret และไม่มี helper เข้ารหัส
- ผู้ใช้/role มาจาก env `DASHBOARD_AUTH_USERS` (admin / sales / staff) · หน้าแอดมินเช็ค cookie เองแบบ `app/quote-logs/page.tsx`
- เทสต์: vitest, `tests/<area>-<topic>.test.ts`, webhook handler ทดสอบด้วย dependency injection (`stubDeps()`), route ทดสอบด้วย `vi.mock`

**ฝั่ง Peak MCP (ทดสอบจริง — รายละเอียดใน README ที่อ้างด้านบน)**
- Endpoint `https://mcp.peakaccount.com/mcp` (Streamable HTTP, protocol `2025-06-18`) · OAuth 2.1: Dynamic Client Registration (public client ไม่มี secret) + PKCE S256 · scope `mcp:read` / `mcp:write`
- access token อายุ **1 ชม.** · refresh token **เปลี่ยนตัวใหม่ทุกครั้งที่ใช้** (ตัวเก่าใช้ไม่ได้อีก)
- ชื่อทูลจริงเป็น **snake_case** (`get_quotation`, `list_quotation`, `search_contacts`) — หน้าเอกสาร Peak เขียน PascalCase ซึ่งผิด
- **session หลุดกลางทางได้**: `HTTP 404 {"code":-32001,"message":"Session not found"}` → ต้อง initialize ใหม่แล้ว retry
- `list_quotation`: ค้น (`searchText`) ได้ด้วย **ชื่อลูกค้าบางส่วน** และ **เลขเอกสารบางส่วน** เท่านั้น — ค้นคำในรายการสินค้าไม่ได้ ค้นรหัสลูกค้าไม่ได้ · ไม่ใส่ช่วงวันก็ได้ · ไม่มี sort — **เรียงตามวันที่ออก เก่า→ใหม่ แต่ภายในวันเดียวกันเลขเอกสารมากมาก่อน** (แก้ 2026-11-17 จาก census บน production: เดิมเขียนว่า "เรียงเก่า→ใหม่เสมอ" ซึ่งผิดในระดับวัน — ท้ายรายการคือใบเก่าสุดของวันล่าสุด; เลขกับวันที่ออกไม่ตรงกันเสมอด้วย เช่น …188 ออกวันที่ 29 แต่ …187 ออกวันที่ 30) · คืน `totalQuotation` · แถวบาง: มี `code` `issuedDate` `contactCode` `netAmount` แต่ **ไม่มีชื่อลูกค้า ไม่มีรายการ ไม่มีสถานะ**
- `get_quotation {code}`: แถวเต็ม — `status` (`Approve` / `Draft` / `Voided`), ยอดเงิน, `products[]{id, description, quantity, price, vatType, productCode}` · description เป็นข้อความหลายบรรทัดที่เขียนสเปกไว้ (ขนาด / สี-หน้า / กระดาษ / เคลือบ-ปั๊ม) · รายการที่สุ่มทั้งหมดไม่มี `productCode`
- `search_contacts {searchText: <contactCode>}` → ชื่อลูกค้า + ที่อยู่ + เลขผู้เสียภาษี
- `dueDate` ของ Peak = วันออกใบ + 30 วัน (อายุใบเสนอราคา) — **ไม่ใช่วันส่งงาน ห้ามใช้เป็น `dateDue`**
- วันที่ทุกตัวเป็น `yyyyMMdd` · ข้อความไทยมาเป็น `\uXXXX` ใน JSON text (parse ปกติ)
- latency ต่อ call 0.2–1.5 วิ · rate limit ไม่ทราบ
- `products[].id` (GUID ต่อบรรทัด) มีทุกบรรทัดและ **คงที่ข้าม session** (ทดสอบแล้ว) → ใช้เป็น key ของ "รายการ" ได้
- **OAuth callback แบบ https บน domain จริงใช้ได้** (ทดสอบแล้ว): ลงทะเบียน client ด้วย `redirect_uri = https://dashboard.penprinting.co/api/admin/peak/callback` ได้ 201 และ `/oauth/authorize` redirect ไป `secure.peakaccount.com/mcpConnect` โดยไม่มี error
- ข้อมูลที่สุ่ม (38 ใบล่าสุด ณ 2026-11-14): **26 ใบรายการเดียว · 10 ใบ 2 รายการ · 2 ใบ 3 รายการ** (≈ 1 ใน 3 มีหลายรายการ) · ทุกใบสถานะ `Approve` · ใบหลายรายการมีทั้ง (ก) งานพิมพ์คนละงานจริง (ปฏิทินตั้งโต๊ะ + แคตตาล็อค) (ข) งานเดียวกันคนละจำนวน/แบบ (ค) **บรรทัดที่ไม่ใช่งานพิมพ์** เช่น "ค่าจัดส่ง", "ขออนุญาติติดตั้ง ราคาต่อ 1 เดือน", ค่าไดคัทที่เป็นส่วนประกอบของรายการก่อนหน้า
- **ชื่อลูกค้าใน Peak = ชื่อแบบเดียวกับที่แดชบอร์ดใช้**: เทียบ 24 ลูกค้าจากใบล่าสุดกับ `public/customers.json` (1,637 ชื่อ) → ตรงกันทุกตัวอักษร 14 · คล้ายแต่ไม่ตรง **0** · ไม่มีในลิสต์ 10 (ลูกค้าใหม่ที่เพิ่มใน Peak หลังลิสต์ถูก export) — ลิสต์ของแดชบอร์ดคือ export จาก Peak อยู่แล้ว

**เครดิต Peak**: อ่าน/ค้น = ฟรี (เฟสนี้ 0 เครดิต) · สร้างเอกสาร 1 เครดิต/ใบ (เฟส 2)

## 4. ประสบการณ์ในกลุ่ม LINE (ตัดสินแล้วกับคุณนุ๊ก)

> **คำว่า "ร่าง" ในเอกสารนี้ = ร่างใน LINE** (การ์ดที่ยังเลือกไม่ครบ + state ชั่วคราวฝั่งระบบ) — **ไม่ใช่ "ใบร่าง" ของแดชบอร์ด** (order สถานะ `draft` ในแท็บ "ร่าง" ของ `/orders`) · ร่างใน LINE ไม่โผล่ที่แดชบอร์ดเลยจนกว่าจะกด ✅ สร้างงาน

### 4.1 คำสั่ง

รูปแบบเดียว: `/order` ตามด้วยอะไรก็ได้ (ต้องมี `/` นำ · ไม่สนตัวพิมพ์)

| พิมพ์ | ผล |
|---|---|
| `/order QO-20260900097` | ไปที่ร่างของใบนั้นทันที |
| `/order 900097` (ตัวเลขล้วน) | ค้นเลขบางส่วน — เจอใบเดียว → ร่างทันที · หลายใบ → รายการให้เลือก |
| `/order ไทยฟูดส์` | ใบล่าสุดของลูกค้าที่ชื่อตรง สูงสุด 5 ใบ ให้เลือก |
| `/order ไทยฟูดส์ ไวนิล` | ค้นลูกค้าก่อน แล้วกรองเฉพาะใบที่ข้อความรายการมีคำว่า "ไวนิล" |
| `/order` เฉย ๆ | 5 ใบล่าสุดของทั้งร้าน |

กฎการค้นแบบข้อความ:
- ชื่อลูกค้ามีเว้นวรรคได้ — ลองจับคู่ชื่อลูกค้า **จากยาวไปสั้น** (ทั้งข้อความก่อน แล้วตัดคำท้ายออกทีละคำ) คำที่เหลือถือเป็นคำกรองชื่องาน
- คำกรองเทียบแบบตรงตัว (ไม่สนตัวพิมพ์/ช่องว่างซ้ำ) กับข้อความรายการของใบนั้น ต้องมีครบทุกคำ
- กรองโดยย้อนอ่าน **20 ใบล่าสุด** ของผลค้นนั้น · ถ้ากรองแล้วไม่เหลือ → แสดง 5 ใบล่าสุดแทน พร้อมบอกว่าไม่เจอคำที่ค้น
- ค้นด้วยชื่องานอย่างเดียวไม่ได้ (ข้อจำกัดของ Peak) — ต้องมีชื่อลูกค้าหรือเลขใบนำ

รายการให้เลือก (เรียงใหม่สุดก่อน) แต่ละแถวแสดง: เลขใบ · วันออกใบ · ชื่อลูกค้า · ยอดสุทธิ · บรรทัดแรกของรายการแรก · ป้าย **"✅ เปิดงานแล้ว"** ถ้าใบนั้นเคยเปิดงานจากระบบนี้ · ปุ่มเลือกต่อใบ

```
คุณกิ๊ฟ:  /order ไทยฟูดส์ ไวนิล
น้อง PP:  🔎 "ไทยฟูดส์ อาหารสัตว์" ที่มีคำว่า "ไวนิล" เจอ 2 ใบ
          1) QO-…0097 · 15 ก.ย. · 3,210 บ. · ไวนิลขนาด 1x2 เมตร
          2) QO-…0288 · 4 มิ.ย. · 1,450 บ. · ไวนิล 2x3 เมตร พับขอบ
          [ใบที่ 1] [ใบที่ 2]
```

### 4.2 จากร่างถึงงานบนบอร์ด

```
น้อง PP:  📄 ร่างใบสั่งงาน · QO-20260900097 · ไทยฟูดส์ อาหารสัตว์
          ไวนิลขนาด 1x2 เมตร · จำนวน 10 · 3,210 บ.
          หน่วยของจำนวน:
          [แผ่น] [ชุด] [เล่ม] [กล่อง] [ถุง] [ห่อ] [ชิ้น] [ซอง] [แฟ้ม]   [ยกเลิก]
(แตะ ชิ้น)
          มอบหมายกราฟฟิก:
          [ปุ๊ก] [เปิ้ล] [แอ๊ด] [ไม่ผ่านกราฟฟิก]
(แตะ ปุ๊ก)
          ส่งต่อพิมพ์:
          [SM74] [MO 5สี] [MO] [Hamada] [Inkjet/Copyprint] [Outsource] [ยังไม่ระบุ]
(แตะ Inkjet/Copyprint)
          วันกำหนดส่ง:
          [พรุ่งนี้] [+2 วัน] [+3 วัน] [+5 วัน] [+7 วัน] [📅 เลือกวันเอง]
(เลือก 20 พ.ย.)
          สรุป: ไวนิลขนาด 1x2 เมตร · 10 ชิ้น · ไทยฟูดส์ อาหารสัตว์
          กราฟฟิก ปุ๊ก · ส่งต่อพิมพ์ Inkjet/Copyprint · ส่ง 20 พ.ย. · ผู้สั่งงาน กิ๊ฟ
          [✅ สร้างงาน] [📝 บันทึกเป็นใบร่างในแดชบอร์ด] [ยกเลิก]
(แตะ ✅)
          ✅ เปิดงานแล้ว #<orderId> … [เปิดใบสั่งงาน] [พิมพ์ใบสั่งงาน]
```

**สองทางให้เลือก (คุณนุ๊กขอ 2026-11-14): "สั่งเลย" หรือ "ทำเป็นใบร่างในแดชบอร์ด"**

ทุกใบเดินขั้นเดียวกันจนถึง **การ์ดสรุป** แล้วเลือกที่นั่น (คุณนุ๊กกำหนดตำแหน่งปุ่ม: อยู่ที่การ์ดสรุปที่เดียว)

- **✅ สร้างงาน** = งานขึ้น /board ทันที
- **📝 บันทึกเป็นใบร่างในแดชบอร์ด** = สร้าง **ใบร่างของแดชบอร์ด** (order สถานะ `draft` — อยู่ในแท็บ "ร่าง" ของ `/orders`, **ยังไม่ขึ้นบอร์ด ไม่มี job**) ที่มีข้อมูลจาก Peak (ลูกค้า ชื่องาน จำนวน หมายเหตุ) **และทุกอย่างที่เลือกใน LINE** (หน่วย กราฟฟิก ส่งต่อพิมพ์ วันส่ง ผู้สั่งงาน) → น้อง PP ตอบ "📝 บันทึกเป็นใบร่างแล้ว #<orderId>" + ปุ่ม [เปิดใบร่างในแดชบอร์ด] → ไปเติมสเปกแล้วกดส่งงานจากฟอร์มตามปกติ (flow ใบร่างเดิมของแดชบอร์ด ไม่แก้อะไร)
- **ยกเลิก** = ทิ้งร่างใน LINE ไม่เกิดอะไรในแดชบอร์ด

- **หน่วยของจำนวน** (คุณนุ๊กขอ 2026-11-14): เลือกจากรายการเดียวกับฟอร์มแดชบอร์ด (`QTY_UNITS` — วันนี้คือ แผ่น ชุด เล่ม กล่อง ถุง ห่อ ชิ้น ซอง แฟ้ม) · ถามทุกหน่วยงานที่มีจำนวน (แบบรวมหลายรายการไม่มีจำนวนเดียว → ข้ามขั้นนี้) · รวมเป็น 5 แตะต่อใบ
- กฎเดียวกับฟอร์ม: ต้องมีกราฟฟิกหรือเครื่องพิมพ์อย่างน้อยหนึ่ง → ถ้าแตะ "ไม่ผ่านกราฟฟิก" ขั้นส่งต่อพิมพ์จะ **ไม่มี** ปุ่ม "ยังไม่ระบุ"
- รายชื่อปุ่มมาจาก `QTY_UNITS` / `STAFF.graphic` / `STAFF.print` ตัวเดียวกับที่ฟอร์มใช้ (ไม่ hard-code ซ้ำ — แก้รายการในแดชบอร์ดแล้ว LINE เปลี่ยนตาม)
- "📅 เลือกวันเอง" = datetimepicker ของ LINE (โหมด date, ไม่ให้เลือกวันก่อนวันนี้) · ปุ่ม +N วัน มีไว้ให้เครื่องที่ picker ใช้ไม่ได้ (LINE บนคอมบางรุ่น) ยังทำงานได้ · วันคิดตามเวลาไทย
- การ์ด "เปิดงานแล้ว" แสดงข้อมูลชุดเดียวกับ success modal ของฟอร์ม (เลขงาน, PIN) + ลิงก์ไปหน้าแก้ไขและหน้าพิมพ์ของแดชบอร์ด

### 4.3 ใบที่มีหลายรายการ

ใบที่มี **รายการเดียว** ข้ามขั้นนี้ ใบที่มี **มากกว่า 1 รายการ** ร่างแสดงทุกรายการ แล้วถาม:

```
          [รวมเป็น 1 งาน] [แยกเป็น 4 งาน] [ยกเลิก]
```

- **รวม**: 1 ใบสั่งงาน ชื่องาน = บรรทัดแรกของรายการแรก + " (+3 รายการ)" · ทุกรายการอยู่ในหมายเหตุ (เหมาะกับใบที่บรรทัดอื่นเป็นค่าจัดส่ง/ส่วนประกอบของงานเดียวกัน) · ไม่มีขั้นเลือกหน่วย → การ์ดแรกคือขั้นเลือกกราฟฟิก · การ์ดสรุปมี 3 ปุ่มเหมือนกัน
- **แยก**: ทำทีละรายการตามลำดับ ("รายการที่ 2/4: …") การ์ดแรกของแต่ละรายการ (ขั้นเลือกหน่วย) **มีปุ่ม [ข้ามรายการนี้]** ด้วย (สำหรับบรรทัดที่ไม่ใช่งานพิมพ์ เช่น ค่าจัดส่ง) · แต่ละรายการเลือกที่การ์ดสรุปของตัวเองว่าจะสร้างงานหรือบันทึกเป็นใบร่าง · รายการที่ไม่ข้ามผ่านขั้น หน่วย → กราฟฟิก → ส่งต่อพิมพ์ → วันส่ง → ยืนยัน แล้วสร้างทันทีก่อนไปรายการถัดไป · ตั้งแต่รายการที่ 2 หลังเลือกหน่วยแล้วมีปุ่ม **[เหมือนใบก่อน]** (ใช้กราฟฟิก/เครื่องพิมพ์/วันส่งชุดเดิม → ไปหน้าสรุปเลย — **หน่วยไม่ลอก** เพราะเป็นของแต่ละรายการ) · หยุดกลางทางได้ รายการที่สร้างแล้วคงอยู่
- "ข้าม" **ไม่ถูกจำถาวร** — แปลว่า "ยังไม่ได้เปิดงานจากบรรทัดนี้" เท่านั้น กลับมาเปิดทีหลังได้ (ดู 4.5)

### 4.4 ใครคือผู้สั่งงาน

ครั้งแรกที่ LINE user คนหนึ่งใช้ `/order` น้อง PP ถาม "คุณคือใคร" ด้วยปุ่มจาก `ORDERERS` (นุ๊ก / กิ๊ฟ / เจี๊ยบ) + ปุ่ม **[ไม่ใช่ฉัน]** (กดออก ไม่ทำอะไรต่อ) → เลือกแล้ว **จำไว้ถาวร** และทำคำสั่งเดิมต่อให้เลย ครั้งถัดไปไม่ถามอีก ผู้สั่งงานของใบ = คนที่พิมพ์ `/order`

**คุณนุ๊กตัดสิน (2026-11-14): เลือกชื่อเองได้ ไม่ต้องมีขั้นอนุมัติ** — กลุ่มที่จะใช้มีแค่นุ๊กกับกิ๊ฟ สิทธิ์ใช้ `/order` = การเป็นสมาชิกกลุ่มที่อนุญาต (`PEAK_ORDER_GROUP_IDS`) · ด้วยเหตุเดียวกัน **การ์ดแสดงยอดเงินของใบเสนอราคาได้** · ถ้าวันหนึ่งกลุ่มนี้มีทีมผลิตเข้ามา หรือจะเปิดให้กลุ่มอื่นใช้ ต้องกลับมาทบทวน 2 เรื่องนี้ (ขั้นอนุมัติในหน้าแอดมิน + ซ่อนยอดเงิน) ก่อนเพิ่ม group id

### 4.5 กันซ้ำ / ของค้าง / สิทธิ์

- **ใบเสนอราคา 1 ใบ เปิดงานได้ชุดเดียว** (ทุกงานมีใบของตัวเอง) — `/order` กับใบที่เคยเปิดงานแล้วจะ **ไม่เริ่มร่างใหม่** แต่ตอบ "การ์ดสถานะ": งานที่เปิดไปแล้ว (เลขงาน + ลิงก์)
  - เปิดแบบเดี่ยว/รวมไปแล้ว → จบแค่นั้น
  - เปิดแบบแยกและยังมีบรรทัดที่ไม่มีงาน (ข้ามไว้ หรือหยุดกลางทาง) → แสดงบรรทัดที่เหลือ + ปุ่ม **[เปิดรายการที่เหลือ]** (เข้าโหมดแยกเฉพาะบรรทัดที่เหลือ) — ไม่มีสถานะ "ครบ/ไม่ครบ" ให้ต้องปิด
  - งานที่เคยเปิดถูก **ยกเลิก** ในแดชบอร์ดแล้ว → บรรทัดนั้นถือว่าว่าง เปิดใหม่ได้. "ยกเลิกแล้ว" ใช้นิยามเดียวกับที่แดชบอร์ดแสดง (`lib/order-lock.ts` / `lib/orders-list.ts`): **ยกเลิกทั้งใบสั่งงาน** (`orders.status = 'cancelled'`) **หรือยกเลิก job จากการ์ดบนบอร์ด** (ใบยังเป็น `sent` แต่มีแถวใน `cancelled`) — v2 ไม่มีการลบ order จริง; แถวหายก็นับเหมือนกัน *(แก้ไข 2026-11-16 — คุณนุ๊กยืนยัน; เดิมเขียนเฉพาะ `orders.status`)*
  - **กู้คืน job ที่ยกเลิกไว้** (ปุ่ม "กู้คืน" ที่หน้า /cancelled) **ทำไม่ได้** ถ้าบรรทัดของใบนั้นถูกเปิดเป็นใบสั่งงานใหม่ไปแล้ว หรือมีคนกำลังเปิด/กู้จากใบเสนอราคาเดียวกันอยู่ — ระบบปฏิเสธพร้อมบอกเลขใบใหม่ (ถ้าต้องการใช้ใบเดิม ให้ยกเลิกใบใหม่ก่อนแล้วกู้อีกครั้ง). ถ้าบรรทัดยังว่าง กู้คืนได้ตามปกติ และบรรทัดกลับมาผูกกับใบเดิม. งานที่ไม่ได้มาจาก `/order` กู้คืนได้เหมือนเดิมทุกอย่าง *(เพิ่ม 2026-11-16 — คุณนุ๊กสั่ง)*
  - **ใบร่างของแดชบอร์ดที่สร้างจาก `/order` นับเป็น "เปิดแล้ว" เหมือนกัน** — การ์ดสถานะแสดงว่าเป็นใบร่าง (ยังไม่ส่งงาน) + ลิงก์เปิดในแดชบอร์ด ไม่สร้างใบที่สองจากใบเสนอราคาเดียวกัน · ใบร่างถูกยกเลิก → เปิดใหม่ได้ · ใบร่างถูกส่งงานจากแดชบอร์ด → เป็นงานปกติ
- ถ้ามีใบสั่งงานที่ยังทำอยู่ซึ่ง **ชื่องาน + ลูกค้าตรงกัน** (กฎ duplicate เดิมของฟอร์ม) → ถามยืนยันอีกชั้น `[สร้างต่อ] [ยกเลิก]` เหมือนที่ฟอร์มเตือน
- ร่างที่ไม่มีการแตะต่อ **30 นาที** หมดอายุ — แตะปุ่มเก่าจะได้ข้อความให้พิมพ์ `/order` ใหม่
- แตะปุ่มของขั้นที่ผ่านไปแล้ว / แตะซ้ำ → ไม่เกิดอะไร (เงียบ) · ปุ่มยืนยันถูกแตะซ้ำ → ไม่สร้างซ้ำ
- **เฉพาะคนที่พิมพ์ `/order` แตะปุ่มของร่างนั้นได้** — คนอื่นแตะจะได้ข้อความสั้น ๆ ว่าเป็นร่างของใคร *(Claude ตัดสิน — กันแตะพลาดในกลุ่ม)*
- กลุ่มที่ไม่ได้อนุญาต / แชต 1-1 / ปิด flag: `/order` **เงียบสนิท** เหมือนไม่มีคำสั่งนี้ (แชต 1-1 ข้อความไหลไปตามเส้นทางเดิมของมัน)
- ใบสถานะ `Voided` → ปฏิเสธ · สถานะอื่น (`Approve`, `Draft`) → ทำต่อได้ และแสดงสถานะบนร่าง *(Claude ตัดสิน)*

### 4.6 เมื่อมีปัญหา (ข้อความสั้น ภาษาคน)

| สถานการณ์ | น้อง PP ตอบ |
|---|---|
| ยังไม่ได้เชื่อมต่อ Peak / ต่ออายุ token ไม่ได้ | บอกว่าเชื่อมต่อ Peak ไม่ได้ ให้แอดมินกด "เชื่อมต่อ Peak" ที่หน้าแอดมิน |
| Peak ไม่ตอบ / error | บอกว่า Peak ไม่ตอบ ให้ลองใหม่ |
| ค้นไม่เจอ | บอกว่าไม่เจอ + ตัวอย่างวิธีพิมพ์ |
| ร่างหมดอายุ | ให้พิมพ์ `/order` ใหม่ |
| สร้างงานล้มเหลว | บอกว่าสร้างไม่สำเร็จ ร่างยังอยู่ กดยืนยันใหม่ได้ |

## 5. ข้อมูลที่ลงใบสั่งงาน

ต่อ 1 ใบสั่งงาน (1 "หน่วย" = ทั้งใบถ้ารายการเดียว/รวม หรือ 1 รายการถ้าแยก) — เริ่มจาก `emptyOrderForm()` แล้วเติม:

| ช่องฟอร์ม | ค่า |
|---|---|
| `name` | บรรทัดแรกที่ไม่ว่างของข้อความรายการ (ตัดเครื่องหมายนำ เช่น `- ` ออก, trim, ตัดความยาวที่ ~120 ตัวอักษร) · แบบรวมหลายรายการ ต่อท้าย ` (+N รายการ)` |
| `customer` | ชื่อลูกค้าจาก Peak **ตามตัวอักษร** (`search_contacts` ด้วย `contactCode` ของใบ, trim) — เป็นชื่อชุดเดียวกับที่ autocomplete ของฟอร์มใช้ (ดู §3) จึงเข้ากับ `/track` กลุ่มลูกค้า, duplicate warning, "ดึงงานล่าสุด" ได้เหมือนงานที่เปิดจากฟอร์ม · ไม่มีขั้นจับคู่ชื่อ/ตาราง alias · หาไม่ได้ → ใช้ `contactCode` |
| `dateIn` | วันนี้ (เวลาไทย) |
| `dateDue` | วันที่เลือกใน LINE |
| `qty` | `quantity` ของรายการ (แบบรวมหลายรายการ → เว้นว่าง จำนวนอยู่ในหมายเหตุ) |
| `qtyUnit` | หน่วยที่เลือกใน LINE (จาก `QTY_UNITS`) — Peak ไม่มีหน่วยให้ จึงให้คนเลือก ไม่เดา · แบบรวมหลายรายการ (ไม่มี `qty`) → ค่า default ของฟอร์ม |
| `notes` | ข้อความรายการ **ทั้งก้อนตามต้นฉบับ** (แบบรวม: ทุกรายการ แยกเป็นบล็อก "รายการ n (จำนวน x): …") + บรรทัดท้าย `อ้างอิง Peak: QO-…` |
| `assignStaff` / `forwardPrint` / `assignDept` | ตามที่เลือก ด้วยกฎเดียวกับ route เดิม |
| `orderer` | ชื่อจาก mapping ของคนที่พิมพ์ `/order` |
| `orderType` | `'normal'` |
| ช่องสเปกอื่นทั้งหมด | ค่า default (ว่าง / ไม่ติ๊ก) |
| `price` (ของ order) | **เว้นว่างเหมือนฟอร์มปัจจุบัน** *(Claude ตัดสิน — ยอดเงินอยู่ใน Peak; ไม่เปลี่ยนสิ่งที่คนบนบอร์ดเห็น)* |

**แบบ "บันทึกเป็นใบร่างในแดชบอร์ด"**: ข้อมูล **ชุดเดียวกับตารางด้านบนทุกช่อง** (เพราะกดได้ที่การ์ดสรุปเท่านั้น ทุกค่าถูกเลือกครบแล้ว) ต่างกันแค่ส่งเป็น `status: 'draft'` (เส้นทาง draft เดิมของ route: ไม่มี job, ไม่เช็ค duplicate ชื่องาน) · เปิดใบร่างในฟอร์มแล้วต้องเห็นหน่วย กราฟฟิก ส่งต่อพิมพ์ วันส่ง ผู้สั่งงาน ถูกเลือกไว้แล้ว

- PIN, สถานะ (`sent` / job `pending` หรือ `draft`), การออกเลข (`mintOrderId` / `mintJobId`), audit, revalidate — **ผ่านตรรกะเดียวกับ `POST /api/orders/add` ทุกอย่าง**
- audit ของงานที่เปิดจาก LINE ต้องดูออกว่ามาจาก LINE และใครเปิด (เช่น user = `กิ๊ฟ (LINE)`) — รูปแบบ role/user ที่หน้า history แสดงได้ไม่พัง → builder
- ความเชื่อมโยง "ใบเสนอราคา ↔ ใบสั่งงาน" **เก็บในตารางของตัวเอง ไม่พึ่ง key ใน `details`** (เพราะ snapshot ถูกเขียนทับเมื่อแก้ไขผ่านฟอร์ม) · บรรทัด `อ้างอิง Peak:` ใน `notes` มีไว้ให้คนอ่าน

### 6.2 `lib/peak/` — เชื่อมต่อ Peak

1. **Token store** — ตารางใหม่เก็บ `client_id`, access token, refresh token (**เข้ารหัส AES-256-GCM** ด้วย key จาก env ใหม่), เวลาหมดอายุ, scope, สถานะ/ข้อผิดพลาดล่าสุด
   - ใช้ access token ที่เหลืออายุพอ (เผื่อ ≥ 5 นาที) ไม่งั้น refresh ก่อน
   - **Refresh ต้องเป็น single-flight ข้าม instance**: refresh token ใช้ได้ครั้งเดียว สอง lambda ที่ refresh พร้อมกันด้วยตัวเดียวกันจะทำให้การเชื่อมต่อพัง → ต้องมีการ "จอง" ระดับ DB (conditional UPDATE … RETURNING) ผู้ชนะ refresh แล้วเขียน token ชุดใหม่ลง DB **ก่อน** ใช้ ผู้แพ้รออ่าน token ใหม่ (รอสั้น ๆ มีเพดาน)
   - **เขียน refresh token ตัวใหม่ลง DB ให้สำเร็จก่อนถือว่า refresh เสร็จ** — ถ้าเขียนไม่สำเร็จ ต้องถือว่าการเชื่อมต่อเสี่ยงพังและบันทึก error
   - ห้าม log token ทุกรูปแบบ
2. **MCP client ขั้นต่ำ** (ไม่ลง dependency ใหม่ถ้าไม่จำเป็น — ต้นแบบที่ใช้งานได้: `peak-integration/peak-mcp/peak-search.mjs`): `initialize` → `notifications/initialized` → `tools/call` · รับได้ทั้ง JSON และ SSE · **404 Session not found → initialize ใหม่ + retry** · 401 → refresh token หนึ่งครั้ง + retry · มี timeout ต่อ call · ไม่ถือ session ข้าม request
3. **ทูลอ่าน 3 ตัวเท่านั้น** — wrapper ที่ type ชัด: `get_quotation`, `list_quotation`, `search_contacts` · **ชื่อทูลเป็น union ปิด** → client นี้เรียกทูลเขียนไม่ได้โดยโครงสร้าง (ชั้นที่สองต่อจาก scope `mcp:read`) · parse ผลแบบระวัง (`resCode`), แปลงเป็น type ภายใน, `yyyyMMdd` → ISO
4. **Helper "ใบล่าสุด N ใบ"**: "ล่าสุด" = **เลขเอกสารมากสุดก่อน** (ลำดับเดียวกับแท็บ "ทั้งหมด" บนเว็บ Peak — คุณนุ๊กกำหนด 2026-11-17). Peak sort ไม่ได้ จึงอ่าน `totalQuotation` → อ่าน **2 หน้าท้าย** พร้อมกัน (51–100 แถว) → เรียงตามเลขเอกสารเอง (`byCodeDesc` ใน `lib/peak/read.ts`) → ตัด N. หน้าท้ายหน้าเดียวไม่พอ เพราะเลขมากสุดของวันล่าสุดอยู่ต้นบล็อกของวันนั้น ซึ่งอาจตกไปอยู่หน้าก่อนสุดท้าย. ข้อจำกัด: ใบที่ตั้งวันที่ออกย้อนหลังไกลกว่าที่ 2 หน้าท้ายครอบคลุมจะไม่ติด "ล่าสุด" (ค้นด้วยเลขยังเจอ). ~~เดิม: Peak เรียงเก่า→ใหม่ ไล่จากหน้าท้ายสุดย้อนขึ้นจนครบ N~~ — ผิด ทำให้ `/order` เฉย ๆ ขึ้น 110–114 ทั้งที่มี 111–120

ข้อมูลจาก Peak ทุกชิ้นเป็น **ข้อความไม่น่าเชื่อถือ** — แสดงเป็น text เท่านั้น ตัดความยาวก่อนใส่การ์ด ไม่นำไปตีความเป็นคำสั่งใด ๆ

### 6.3 เชื่อมต่อ Peak ครั้งแรก — หน้าแอดมิน

- หน้า `/peak` (admin เท่านั้น — วางระดับบนสุดตามแบบ `/registrations` `/quote-logs` + เพิ่มใน middleware matcher และ nav; API อยู่ใต้ `/api/admin/peak/*`): สถานะการเชื่อมต่อ (เชื่อมแล้ว/ยัง, ต่ออายุสำเร็จล่าสุดเมื่อไร, error ล่าสุด, scope) · ปุ่ม **เชื่อมต่อ Peak** · ปุ่ม **ทดสอบ** (เรียกทูลอ่าน 1 ครั้ง) · รายการ mapping LINE user → ผู้สั่งงาน พร้อมปุ่มลบ (ไว้แก้กรณีเลือกชื่อผิด)
- ปุ่มเชื่อมต่อ: (admin session) → ลงทะเบียน client กับ Peak ถ้ายังไม่มี (redirect URI = callback ของ dashboard บน production domain) → PKCE + state → redirect ไป Peak ให้คุณนุ๊กล็อกอิน/ยินยอม → callback ตรวจ admin session + state → แลก token → เข้ารหัสเก็บ → กลับหน้าแอดมิน
- ขอ scope **`mcp:read` เท่านั้น** ในเฟสนี้
- **Keep-alive + ตรวจสุขภาพรายวัน**: cron (Vercel cron, ต้องผ่าน `CRON_SECRET` แบบ morning-report) refresh token วันละครั้ง + เรียกทูลอ่าน 1 ครั้ง → ถ้าล้ม push แจ้ง **กลุ่มที่ใช้ `/order`** (group แรกใน `PEAK_ORDER_GROUP_IDS`) **ไม่เกินวันละครั้ง** พร้อมลิงก์หน้าแอดมิน และแสดงบนหน้าแอดมิน · (อายุ refresh token ตอนไม่ได้ใช้ยังไม่ทราบ — cron นี้ทำให้ไม่ต้องพึ่งคำตอบ)

### 6.4 การเปลี่ยนแปลงฝั่ง LINE

- `parseLineEvents`: postback จาก **กลุ่ม** ให้ผ่านเฉพาะที่ data เป็นของ `/order` (prefix เฉพาะ + เวอร์ชัน) — postback อื่นและรูปจากกลุ่มยังถูกทิ้งเหมือนเดิม · ส่งต่อ `params.date` ของ datetimepicker ด้วย
- `routeInbound`: เพิ่ม route สำหรับ `/order` (ข้อความ) และ postback ของมัน **ก่อน** บรรทัดที่ ignore กลุ่ม · เข้าได้เมื่อ flag เปิด **และ** `groupId` อยู่ในรายการที่อนุญาตเท่านั้น — ไม่ผ่านเงื่อนไข = พฤติกรรมเดิมทุกประการ (`ignore` สำหรับกลุ่ม)
- handler ถูก inject ผ่าน `HandleDeps` (แบบเดียวกับ arm อื่น เพื่อทดสอบด้วย `stubDeps`)
- ปุ่มทุกขั้นเป็น **ปุ่มใน Flex (postback / datetimepicker)** ไม่ใช่ quick reply — ต้องอยู่ในประวัติแชตและใช้ได้ทุกแพลตฟอร์ม แม้มีคนคุยแทรก *(Claude ตัดสิน)* · มี text fallback เมื่อ LINE ปฏิเสธ Flex (แบบ `replyFlexOrText`)
- ทุกคำตอบใช้ reply token ของ event นั้น (ฟรี) · push ใช้เฉพาะ fallback เดิมของ adapter และการแจ้งเตือนจาก cron
- เคารพข้อจำกัดของ LINE: postback data ≤ 300 ตัวอักษร, ความยาว label/ข้อความในการ์ด, ≤ 5 messages ต่อ reply

### 6.5 `lib/peak-order/` — คำสั่ง, ร่าง, state

- **Parser คำสั่ง** (pure): แยก `/order` + รูปแบบ argument ตาม §4.1
- **Resolver** : argument → ร่างของใบเดียว หรือ รายการให้เลือก หรือ ไม่เจอ (ใช้ `lib/peak`) · จำกัดจำนวน call ต่อคำสั่งและ concurrency (rate limit ของ Peak ไม่ทราบ — เริ่มแบบระวัง เช่น ≤ 3 พร้อมกัน, เพดานรวมต่อคำสั่ง) · งานทั้งหมดต้องจบในงบเวลาของ `after()` (60 วิ) โดยมีเป้าตอบภายใน ~5–8 วิ
- **ร่าง (draft)** — ตารางใหม่ 1 แถวต่อร่าง: id สั้นสุ่ม (ไปอยู่ใน postback data), group, LINE user ผู้เริ่ม, ผู้สั่งงาน, snapshot ของใบเสนอราคา ณ ตอนเริ่มร่าง (ลูกค้า + รายการ + ยอด + สถานะ), โหมด (เดี่ยว / รวม / แยก), แผนต่อหน่วย (ตัวเลือกที่เลือกแล้ว + ผลการสร้าง), ขั้นปัจจุบัน, เวลาแตะล่าสุด
  - รายการให้เลือก (§4.1) **ไม่ต้องมีแถว** — ปุ่มพกเลขใบไปใน postback แล้วค่อยสร้างร่างเมื่อเลือก
  - ร่างใช้ snapshot ตอนเริ่ม ไม่อ่าน Peak ซ้ำตอนยืนยัน (ใบถูกแก้ใน Peak ระหว่าง 30 นาทีนั้น → ใบสั่งงานเป็นข้อมูลตอนเริ่มร่าง — ยอมรับได้)
- **State machine**: ทุกการแตะ = conditional `UPDATE … WHERE id AND ขั้นปัจจุบัน = ขั้นที่ปุ่มนั้นเป็นของ … RETURNING` เป็น statement แรก — ได้ 0 แถว = แตะซ้ำ/ขั้นเก่า → เงียบ (pattern เดียวกับ "conditional gate first" ใน PATTERNS) · ตรวจ: กลุ่มตรง, ผู้แตะ = ผู้เริ่ม, ยังไม่หมดอายุ
- **กันสร้างซ้ำ (สำคัญสุด)** — ตาราง link ใหม่ มี unique key ต่อ `(เลขใบเสนอราคา, บรรทัด)` โดยบรรทัด = line id ของ Peak (ไม่มี id → ลำดับ) — **กติกาเดียว: 1 บรรทัดของใบเสนอราคา ผูกกับใบสั่งงานที่ยังไม่ถูกยกเลิกได้ใบเดียว** · งานแบบเดี่ยว/รวม จอง **ทุกบรรทัด** ของใบในคำสั่งเดียว (ได้ไม่ครบ = ถอยทั้งหมด) · งานแบบแยกจองบรรทัดเดียว:
  1. **จองแถว link ก่อน** (INSERT … ON CONFLICT DO NOTHING RETURNING) — ผู้ชนะเท่านั้นไปต่อ
  2. สร้าง order + job ผ่าน `lib/orders-create`
  3. เขียน `order_id` ลงแถว link + อัปเดตร่าง
  - ถ้าตายระหว่าง 1–3: แถวที่จองแล้วแต่ไม่มี `order_id` และเก่าเกินเกณฑ์สั้น ๆ → ให้ความพยายามครั้งถัดไป "รับช่วง" ได้ **โดยต้องเช็คก่อนว่า order ถูกสร้างไปแล้วหรือยัง** (ไม่ให้เกิดงานซ้ำจากการ retry)
  - แถว link ที่ชี้ไป order ที่ถูกยกเลิกแล้วตามนิยาม §4.5 (ยกเลิกทั้งใบ · ยกเลิก job จากบอร์ด · หรือแถว order หาย) → ถือว่าว่าง เปิดใหม่ได้
  - **ทางกู้คืนต้องผ่าน gate เดียวกับทางสร้าง** *(เพิ่ม 2026-11-16)* — `/api/jobs/restore` ของใบที่มี marker จาก Peak: ก่อนลบแถว `cancelled` ให้จองบรรทัดคืนด้วยวิธีเดียวกับขั้น 1 (id ของการจองไม่ซ้ำต่อ request) แล้วเช็ค marker เหมือนการรับช่วง → จองไม่ได้ = ตอบ 409 ไม่กู้ · กู้สำเร็จ = เขียน `order_id` ของใบเดิมกลับลงแถว link · กู้ล้ม = ปล่อยการจอง · ตัวเช็คเองล่ม = ไม่กู้ (502) · ใบที่ไม่มี marker ไม่แตะตาราง link เลย (`lib/peak-order/restore-guard.ts`). เหตุผล: "ยกเลิก job จากบอร์ด" เป็นสถานะที่ย้อนกลับได้ — ถ้าไม่กัน การกู้คืนจะทำให้ใบเก่าฟื้นมาอยู่คู่กับใบใหม่บนบรรทัดเดียว
  - ด้วยกติกาต่อบรรทัดนี้ "รวม" กับ "แยก" ของใบเดียวกันกันกันเองโดยโครงสร้าง (เปิดแบบรวมแล้วไม่มีบรรทัดว่างให้แยก และกลับกัน)
- **Mapping LINE user → ผู้สั่งงาน** — ตารางใหม่ (LINE userId, ชื่อใน `ORDERERS`, display name ตอนลงทะเบียน) · event ที่ไม่มี `userId` → ตอบว่าระบุตัวผู้ใช้ไม่ได้ ไม่ทำต่อ
- **Flex builders** (pure, ทดสอบ snapshot ได้): รายการให้เลือก, ร่าง + ขั้นต่าง ๆ, สรุป/ยืนยัน, เปิดงานแล้ว, ข้อความปัญหา
- **Mapper** ใบเสนอราคา → ข้อมูลฟอร์ม (§5) (pure)

### 6.6 ย้ายตรรกะสร้างออเดอร์ออกจาก route

`app/api/orders/add/route.ts` → ฟังก์ชันฝั่ง server ที่เรียกได้จากทั้ง route และ LINE flow: รับข้อมูลฟอร์ม + ผู้กระทำ (role, user) + ตัวเลือก (`force`) → คืนผลแบบ data (สำเร็จ / duplicate + รายการ / validation errors / ความล้มเหลว) ไม่ใช่ `NextResponse` · route เดิมเหลือเป็น wrapper (auth + แปลงผลเป็น HTTP) **พฤติกรรมและ response เดิมทุกกรณี — เทสต์เดิมต้องเขียวโดยไม่แก้ความคาดหวัง**

ย้าย `ORDERERS` และ `QTY_UNITS` (วันนี้อยู่ใน `app/board/order-form.tsx`) ไปไว้ที่ที่ทั้งฟอร์มและ LINE flow import ได้ (แหล่งเดียว)

## 7. สิ่งที่ปล่อยให้ builder ตัดสิน

- ชื่อ/โครงตาราง, ชื่อไฟล์, รูปแบบ postback data, ชื่อ env ของ key เข้ารหัส
- หน้าตา Flex (โทนให้เข้ากับการ์ดเดิม เช่น `track-flex`) · การจัดปุ่มเมื่อมีหลายปุ่ม · ถ้อยคำข้อความทั้งหมด (ภาษาไทย สุภาพ สั้น)
- ตัวเลขจูน: concurrency/เพดาน call ต่อคำสั่ง, timeout ต่อ call, ระยะรอของ single-flight, เกณฑ์ "จองค้าง" ที่รับช่วงได้
- `limit` สูงสุดต่อหน้าของ `list_quotation` (ทดลองแล้วเลือก) และวิธีไล่หน้าย้อนหลังที่ประหยัด call ที่สุด
- cache ชื่อลูกค้าภายใน invocation
- รูปแบบ role/user ใน audit ที่หน้า history แสดงได้
- จะมีรายการ "ร่างล่าสุด/ข้อผิดพลาดล่าสุด" บนหน้าแอดมินหรือใช้ log อย่างเดียว
- alias ภาษาไทยของคำสั่ง (เช่น `/สั่งงาน`) — ใส่ได้ถ้าไม่ชนข้อความคุยปกติ

## 8. การตรวจรับ

**เทสต์อัตโนมัติ (vitest — ตามแบบเดิมของ repo)**
- parser คำสั่ง · resolver (จับคู่ชื่อลูกค้ายาว→สั้น, ใบล่าสุด N จากหน้าท้าย, กรองคำ, fallback เมื่อกรองไม่เหลือ) ด้วย fixture รูปทรงจริงจาก Peak
- mapper ใบเสนอราคา → ฟอร์ม (บรรทัดแรก, bullet นำ, หลายรายการ, ข้อความยาว)
- state machine: ลำดับปกติ, แตะซ้ำ, แตะขั้นเก่า, คนอื่นแตะ, หมดอายุ, "ไม่ผ่านกราฟฟิก" ต้องบังคับเครื่องพิมพ์, เลือกหน่วย (รวมหลายรายการต้องข้าม), แยกหลายรายการ + "เหมือนใบก่อน" (ไม่ลอกหน่วย) + "ข้ามรายการนี้", หยุดกลางทางแล้วกลับมาเปิดต่อ
- บันทึกเป็นใบร่าง (จากการ์ดสรุปเท่านั้น): order สถานะ `draft` ไม่มี job, ค่าที่เลือกทั้งหมดอยู่ใน snapshot · แตะซ้ำ / แตะ ✅ ตามหลังไม่สร้างซ้ำ · นับเป็น "เปิดแล้ว" ในการ์ดสถานะ
- กันสร้างซ้ำ: ยืนยันซ้ำ / สองร่างของใบเดียวกัน / ตายหลังจอง / รับช่วงเมื่อ order ถูกสร้างไปแล้ว / งานถูกยกเลิกแล้วเปิดใหม่ได้ (ทั้งยกเลิกทั้งใบและยกเลิก job จากบอร์ด) / กู้คืน job เก่าหลังบรรทัดถูกเปิดซ้ำต้องถูกปฏิเสธ รวมกรณีกดกู้ซ้อน 2 ครั้ง *(เพิ่ม 2026-11-16)* — **ต้องทำ mutation check** (ถอด gate แล้วเทสต์ต้องแดง)
- token store: เข้ารหัส-ถอดรหัส, refresh แล้ว persist ตัวใหม่, single-flight (สองผู้เรียกพร้อมกัน refresh แค่ครั้งเดียว), เขียน DB ล้ม
- MCP client: JSON + SSE, 404 → re-init, 401 → refresh, timeout
- `parseLineEvents`: postback กลุ่มของ `/order` ผ่าน / postback กลุ่มอื่นยังถูกทิ้ง / datetimepicker params
- `routeInbound`: flag ปิด, กลุ่มไม่อนุญาต, ห้อง, แชต 1-1 → ผลเดิมทุกกรณี
- `orders/add`: เทสต์เดิมเขียว + parity ของฟังก์ชันที่ย้ายออก
- ตรรกะวันที่รันทั้ง `TZ=UTC` และ `TZ=Asia/Bangkok`
